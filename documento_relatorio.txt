==============================================================================
 A. DIAGNÓSTICO DA DEMANDA
==============================================================================

Instituição:                       RedHosting — Empresa de Hospedagem de Servidores
Área de atuação:                   Tecnologia da Informação / Infraestrutura Web
Público atendido:                  Clientes de hospedagem, desenvolvedores e empresas
Problema identificado:
  A RedHosting possui múltiplos servidores (nodes) espalhados por diferentes
  localidades, incluindo Site, Painel de Controle, Financeiro, e 8 nodes ASC
  (Application Server Containers). A empresa não possuía um painel unificado
  e em tempo real para monitorar o status, latência e disponibilidade desses
  serviços. As informações ficavam dispersas, dificultando a tomada de decisão
  rápida em casos de falha ou degradação.

Processo atual:
  Antes deste projeto, o monitoramento era feito manualmente, com acesso
  individual a cada servidor via terminal, ou através de ferramentas genéricas
  que não ofereciam uma visão consolidada e visual do estado da infraestrutura.

Impactos do problema:
  • Dificuldade em identificar rapidamente nodes offline
  • Atraso na resposta a incidentes
  • Falta de métricas históricas para planejamento de capacidade
  • Impossibilidade de demonstrar visualmente a saúde da infraestrutura
    para stakeholders não-técnicos

==============================================================================
 B. LEVANTAMENTO DE REQUISITOS
==============================================================================

Stakeholders identificados:
  • Equipe de infraestrutura da RedHosting
  • Gestores de TI
  • Clientes (indiretamente, através da transparência do serviço)

Requisitos Funcionais (RF):

  RF-01: O sistema deve consumir a API de status da RedHosting
         (GET https://api-status.redhosting.com.br/api/status)
  RF-02: O sistema deve exibir cards com métricas gerais (total de nodes,
         nodes online, nodes offline, percentual de uptime)
  RF-03: O sistema deve listar todos os nodes com nome, status, latência,
         e disponibilidade individual
  RF-04: O sistema deve atualizar os dados automaticamente a cada 30 segundos
  RF-05: O sistema deve permitir atualização manual dos dados via botão
  RF-06: O sistema deve exibir gráficos visuais de distribuição de status,
         latência por node e uptime
  RF-07: O sistema deve gerar alertas automáticos quando um node apresentar
         latência elevada ou ficar offline
  RF-08: O sistema deve manter um histórico de logs com eventos do sistema
  RF-09: O sistema deve oferecer alternância entre tema escuro e claro
  RF-10: O sistema deve exibir uma página de configurações com informações
         do projeto e dados institucionais

Requisitos Não Funcionais (RNF):

  RNF-01: O sistema deve ser acessível via navegador web (Chrome, Firefox, Edge)
  RNF-02: O sistema deve ser responsivo (desktop, tablet e mobile)
  RNF-03: A interface deve seguir design dark mode com paleta roxo/azul
  RNF-04: O backend deve utilizar Python com Flask
  RNF-05: O frontend deve utilizar HTML5, CSS3 e JavaScript puro (sem frameworks)
  RNF-06: Os gráficos devem ser renderizados com Chart.js
  RNF-07: O sistema deve tratar erros de API externa com fallback e dados demo
  RNF-08: O tempo de resposta da interface deve ser inferior a 2 segundos
  RNF-09: O sistema deve ser implantado via Docker em servidor Linux

Restrições do Projeto:
  • Prazo: 1 semestre letivo
  • Equipe: 2 estudantes
  • Orçamento: Nenhum (ferramentas gratuitas e VPS própria)
  • API externa deve ser consumida via backend para evitar CORS

==============================================================================
 C. PROPOSTA DE SOLUÇÃO
==============================================================================

Objetivo do sistema:
  Desenvolver um painel de monitoramento em tempo real para a infraestrutura
  de servidores da RedHosting, permitindo que a equipe visualize rapidamente
  a saúde de todos os nodes, identifique problemas e tome decisões ágeis.

Público usuário:
  Equipe de infraestrutura e gestores de TI da RedHosting.

Principais funcionalidades:
  • Dashboard com KPIs (cards de métricas)
  • Gráficos interativos (distribuição, latência, uptime)
  • Lista detalhada de nodes com status e indicadores visuais
  • Sistema de alertas automáticos (crítico, atenção, informativo)
  • Logs de eventos do sistema
  • Alternância de tema (dark/light)
  • Atualização automática a cada 30 segundos

Escopo do MVP:
  O MVP inclui todas as funcionalidades acima, entregando um painel completo
  e funcional que consome dados reais da API da RedHosting.

 G. REGISTRO DAS SPRINTS + RETROSPECTIVAS

SPRINT 1 — Setup e API
──────────────────────

Funcionalidades desenvolvidas:
  • Criação do servidor Flask com rota principal (/) e rota da API (/api/dados)
  • Implementação da função consultar_api_externa() com tratamento de timeout,
    erro de conexão e exceções genéricas
  • Proxy da API externa (https://api-status.redhosting.com.br/api/status)
    para evitar problemas de CORS
  • Rota de health check (/api/health)

Problemas encontrados:
  • A API externa retorna os dados em formato complexo: latency e uptime como
    objetos aninhados, não como números simples
  • Foi necessário criar uma função de transformação (transformar_dados) para
    converter latency.avg → número e uptime.24h → número
  • Sem essa transformação, o frontend não conseguia renderizar os dados

Evidências:
  • [Print do código da função transformar_dados()]
  • [Print do terminal mostrando o Flask rodando]

Retrospectiva:
  Pontos positivos:  Estrutura do projeto ficou limpa e organizada
  Pontos de melhoria: Testar a API real antes de começar o frontend
  Ações p/ sprint 2:  Criar o dashboard com cards e tabela usando os dados
                       já transformados


SPRINT 2 — Dashboard Básico
───────────────────────────

Funcionalidades desenvolvidas:
  • 4 cards de métricas: Total de Serviços, Operacionais, Falha, Uptime

==============================================================================
 J. REFLEXÃO CRÍTICA
==============================================================================

Aprendizados desenvolvidos:
  • Integração com API externa: Consumir uma API real e tratar seus dados
    no formato correto foi um dos maiores aprendizados. Descobrimos que
    APIs reais raramente retornam os dados no formato que esperamos —
    foi necessário criar uma camada de transformação
  • CORS e proxy: Entendemos na prática por que o CORS existe e como um
    backend proxy resolve esse problema
  • Design system: Criar um tema coeso (cores, tipografia, espaçamentos)
    foi essencial para um resultado profissional
  • Docker e deploy: Empacotar a aplicação em Docker e fazer deploy em
    uma VPS foi um desafio que trouxe confiança para projetos futuros
  • Tratamento de erros: Aprender a pensar em todos os cenários de falha
    (API fora do ar, timeout, rede instável) e criar fallbacks adequados

Desafios enfrentados:
  • Formato inesperado da API (latency e uptime como objetos)
  • Configuração de SSH da máquina Windows para a VPS Linux
  • Gerenciamento de CSS specificity para os painéis de navegação
  • Manter a consistência visual entre tema dark e light

Reflexão sobre a experiência extensionista:
  Este projeto foi além de um exercício acadêmico — resolvemos um problema
  real de uma empresa real. Ver o sistema rodando em produção e sendo
  utilizado pela equipe da RedHosting trouxe uma satisfação que vai além
  da nota. A experiência mostrou que a faculdade pode, sim, gerar impacto
  direto na comunidade, e que o conhecimento técnico aliado à vontade de
  resolver problemas pode criar soluções valiosas.
